# Balance File Import and Month Close Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Once a month the app asks for Leumi's exports. Uploading them:
- updates the bank balance;
- ignores card settlement lines;
- links fixed items and income to their real rows;
- confirms transactions already captured (Google Pay, manual) and adds the missing ones;
- puts anything uncertain into a review screen, which also shows unreadable phone notifications.

**Architecture:**
- **Parsing:** Excel files are read in the browser into plain row arrays (`src/import/sheets.ts`). Bank-specific parsers turn those rows into `ImportedRow`s.
- **Decisions:** pure planners in `src/import/plan.ts` decide every update, insert and review flag. They have no I/O and are fully unit-tested.
- **Writing:** a thin repo (`src/data/importRepo.ts`) carries the plan out with ordinary RLS-scoped writes.
- **Idempotency:** a per-household unique `import_key` makes re-uploading a file a no-op.

**Tech Stack:**
- Existing: Vite, React 18, TypeScript, Supabase, Vitest and PGlite.
- New: `read-excel-file` (MIT, browser and node entries) for `.xlsx`.
- Fixtures: generated by a committed Python script (openpyxl) with made-up data.

**Spec:** `docs/superpowers/specs/2026-11-06-balance-design.md`, §6.2 (checking rows, card settlement), §6.6, §7.2–7.5. This is plan 2 of the roadmap (`2026-11-06-balance-roadmap.md`). Category rules and recurring detection (§7.4) move to plan 2b.

## Global Constraints

- **Free only.** No new paid service, and no server code beyond SQL migrations.
- **Privacy:** real exports are never committed. They hold names and an ID number. Fixtures use invented names, ID `000000000` and card `1111`.
- **Matching** is by **amount + date ±1 day + card last 4**, never by merchant name (spec §7.5: names differ between Google Pay and the file).
- **File data wins** on a match: date, amount, merchant (the Hebrew name from the file) and status `confirmed`. A user-set `category_id`, `recurring_item_id` and `fund_id` are kept.
- **Card settlement lines** in the checking export (`לאומי ויזה`, `לאומי מאסטרקרד`, `ישראכרט`, `כאל`, `מקס`, `max`) are imported with `is_card_settlement = true` and never counted.
- **Money, dates and copy:**
  - Money in integer agorot; dates `YYYY-MM-DD`; month and week math as in plan 1.
  - Hebrew UI, RTL, logical CSS, in-app confirm only.
- **Leumi card export layout** (observed 2026-11-17):
  - **Header rows:** row 1 is `"<name>-<id>"`, row 2 is `"<last4>-<card name>"`, row 3 is the billing month `"MM/YYYY"`, and row 4 holds the column headers.
  - **Data and total:** data rows follow until an empty row; then comes `סך הכל`, and the next row carries the total, e.g. `3172.48₪`.
  - **Columns** (by header text):
    - `תאריך עסקה` (`DD-MM-YYYY`), `שם בית העסק`, `קטגוריה`, `4 ספרות אחרונות של כרטיס האשראי`, `סוג עסקה`;
    - `סכום חיוב`, `סכום עסקה מקורי`, `מטבע עסקה מקורי`, `תאריך חיוב`;
    - `הערות` (for installments: `תשלום 6 מתוך 10`).
  - **Sheets:**
    - `עסקאות במועד החיוב`: charged. Use `סכום חיוב`.
    - `עסקאות שאושרו וטרם נקלטו`: pending. `סכום חיוב` is empty, so use `סכום עסקה מקורי`.
    - `עסקאות חו"ל ומט"ח`: charged, foreign. Use `סכום חיוב`, which is ₪.

## Review Focus

1. **The same file uploaded twice, or a pending row later re-exported as charged:** no duplicate transactions. The `import_key` must not contain status or sheet. Test in Task 6 (`planCardImport is idempotent across pending→charged`).
2. **Two identical purchases on the same day (two 12 ₪ coffees), one captured by Google Pay:** match exactly one, add exactly one, and never merge both into one. Test in Task 3.
3. **A Google Pay transaction dated the 17th that the file dates the 16th:** they match. Test in Task 3.
4. **An installment row (`תשלום 6 מתוך 10`, purchase 22-06-2026):** it lands in the month of installment 6, 2026-11-22, with that month's charge amount. Test in Task 2.
5. **A checking statement where salary differs from the expected amount, and rent is paid by cheque `שיק`:** each links to its fixed item, and doesn't also count as variable spending. Test in Task 5.

### Task 3: Match imported rows to captured transactions

**Files:**
- Create: `src/engine/match.ts`
- Modify: `src/engine/types.ts` (`Txn` gains `cardLast4: string | null`, `importKey: string | null`, `needsReview: boolean`), `src/data/mappers.ts`, `tests/fixtures/engine.ts` (defaults `null`, `null`, `false`)
- Test: `tests/engine/match.test.ts`

**Interfaces:**
- Produces:

```ts
export interface MatchResult {
  matched: { txnId: string; row: ImportedRow }[];
  unmatched: ImportedRow[];      // to insert
  ambiguous: ImportedRow[];      // to insert with needsReview
}
export function matchRows(existing: Txn[], rows: ImportedRow[]): MatchResult;
```

- Rules:
  - A candidate is an existing `kind:'expense'` txn with `importKey === null`, the same amount, `|date diff| <= 1`, and the same `cardLast4` when both are known.
  - Each existing txn is used at most once.
  - When a row has candidates but they can't be told apart, it goes to `ambiguous`. Two rows of one key group competing for one txn counts as such a case: match only one row to it, and send the others to `unmatched`, not `ambiguous`.
  - Rows whose `importKey` already exists among `existing` are dropped from all three lists, since they were already imported.

  - `two captured txns that both fit one row: the row is ambiguous`.

### Task 6: Import planners

**Files:**
- Create: `src/import/plan.ts`
- Test: `tests/import/plan.test.ts`

**Interfaces:**
- Consumes: `matchRows`, `leumiCategoryToOurs`, `linkRecurring`, `CardFile`, `CheckingFile`.
- Produces:

```ts
export interface TxnUpdate { id: string; patch: Partial<TxnRowPatch> }   // TxnRowPatch = snake_case columns
export interface ImportPlan {
  updates: TxnUpdate[]; inserts: Omit<TxnRow, 'id'>[];
  bankBalance: { amount: Agorot; asOf: ISODate } | null;
  summary: { matched: number; added: number; review: number; skipped: number };
}
export function planCardImport(file: CardFile, existing: Txn[], categories: Category[], householdId: string, memberId: string): ImportPlan;
export function planCheckingImport(file: CheckingFile, existing: Txn[], items: RecurringItem[], householdId: string, memberId: string): ImportPlan;
```

- **On a card match:** the update sets `date`, `amount_agorot`, `merchant` (from the file), `status: 'confirmed'` (or keeps `pending` when the row is pending), `card_last4`, `import_key` and `category_name_hint`. It sets `category_id` only when the txn has none.
- **Card inserts:** `source:'file'`, `kind:'expense'`, `status` per row, `needs_review` for ambiguous rows. A refund stays an expense with a negative amount.
- **Checking inserts:** every row is inserted with `source:'file'`, `is_card_settlement` per row, and `recurring_item_id` from `linkRecurring`. A row matching an existing txn by `import_key` is skipped.
- **The month for `linkRecurring`:** the month of each row's own date.
